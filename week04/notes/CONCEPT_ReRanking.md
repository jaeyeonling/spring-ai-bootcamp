# ReRanking (LLM 기반 재순위화)

## 한 문장 정의

> 벡터 검색으로 가져온 후보 문서들을 LLM에게 쿼리 관련성 점수를 매기도록 요청하여 순위를 재조정하는 기법.

## 왜 필요한가

벡터 검색의 코사인 유사도는 "비슷한 주제"를 찾지만, "이 질문에 대한 정확한 답"을 판별하지는 못한다.

Week 02 실험에서 관찰한 예시:
- 질문: "반품 기간이 어떻게 되나요?"
- Top-1 (코사인): 반품 **절차** 설명 문서 (유사하지만 정답 아님)
- Top-3: 반품 **기간** 14일 문서 (정답이지만 순위가 밀림)

코사인 유사도는 "반품"이라는 키워드에 가까운 문서를 모두 높게 평가한다. 하지만 "기간"이라는 세부 의도를 구분하지 못한다. LLM은 쿼리와 문서를 함께 읽기 때문에 이런 미묘한 차이를 잡아낸다.

## 동작 원리

[2-Stage Retrieval](CONCEPT_2Stage_Retrieval.md)의 Stage 2를 LLM으로 구현한다.

```
후보 20개 + 원본 쿼리
        │
        ▼
┌──────────────────────────────────────┐
│ LLM 프롬프트:                         │
│                                      │
│ 쿼리: "반품 기간이 어떻게 되나요?"      │
│                                      │
│ 각 문서의 관련성을 0.0~1.0으로 점수화.  │
│ JSON 배열만 반환. 예: [0.9, 0.3, 0.7] │
│                                      │
│ 문서:                                 │
│ [1] 반품은 14일 이내에 가능합니다...    │
│ [2] 반품 절차: My Orders에서...        │
│ [3] 결제 방법은 카카오페이...           │
│ ...                                   │
└──────────────┬───────────────────────┘
               │
               ▼
       [0.95, 0.7, 0.1, ...]
               │
               ▼
       점수 내림차순 정렬
               │
               ▼
       상위 K개 반환
```

## 프롬프트 설계

### 기본 구조

```
쿼리: '{query}'

각 문서의 관련성을 0.0에서 1.0으로 점수화하세요.
- 1.0: 쿼리에 대한 직접적이고 완전한 답변
- 0.7-0.9: 관련성 높음, 부분적 답변 포함
- 0.3-0.6: 같은 주제지만 직접적 답변 아님
- 0.0-0.2: 관련 없음

점수의 JSON 배열만 반환하세요. 예: [0.9, 0.3, 0.7]

문서:
[1] {문서 1 내용 ~200자}
[2] {문서 2 내용 ~200자}
...
```

### 설계 결정사항

**문서 길이 제한**: 각 문서를 ~200-500자로 truncate한다.
- 이유: 20개 문서 × 500자 = 10,000자 ≈ ~4,000 토큰. 이 이상이면 비용 급증.
- 대부분의 FAQ 청크는 200자 이내이므로 truncate가 거의 불필요.

**출력 형식 강제**: "JSON 배열만 반환"이 핵심.
- LLM이 설명을 덧붙이면 파싱 실패. "다른 텍스트 없이"를 명시적으로 지시.
- 예시(`[0.9, 0.3, 0.7]`)를 넣으면 형식 준수율이 올라감.

**점수 척도 가이드라인**: 0.0~1.0의 의미를 명시하면 점수 분포가 일관적이 됨.
- 가이드라인 없으면 LLM이 모든 문서에 0.5~0.8을 매기는 경향.

## 엣지 케이스 처리

LLM 출력은 비결정적이므로 파싱 실패에 대비해야 한다.

```java
private List<Double> parseScores(String response, int expectedCount) {
    try {
        // LLM이 JSON 배열 앞뒤에 텍스트를 붙일 수 있으므로 배열만 추출
        String jsonArray = extractJsonArray(response);
        List<Double> scores = objectMapper.readValue(jsonArray, 
            new TypeReference<List<Double>>() {});
        
        if (scores.size() != expectedCount) {
            // 점수 수가 안 맞으면 → 재순위화 포기, 원래 순서 유지
            return Collections.nCopies(expectedCount, 0.5);
        }
        return scores;
    } catch (Exception e) {
        // 파싱 실패 → 재순위화 포기, 원래 순서 유지
        return Collections.nCopies(expectedCount, 0.5);
    }
}
```

**Fallback 전략**: 파싱 실패 시 동일 점수를 반환하면 원래 순서(벡터 유사도 순)가 유지된다. "재순위화를 못 하면 원래대로"가 안전한 기본값.

## 전용 Re-Ranker 모델과의 비교

| | LLM 재순위화 (Week 04) | 전용 Cross-encoder |
|-|----------------------|-------------------|
| 모델 예시 | GPT-4o-mini | Cohere Rerank, bge-reranker-v2 |
| 설정 | API 키만 필요 | 별도 API 또는 로컬 배포 |
| 속도 | ~1-2초 (20 문서) | ~100-300ms (20 문서) |
| 비용 | ~$0.0006/호출 | Cohere: $0.001/1000 검색 |
| 정확도 | 충분히 좋음 | 전문 학습되어 더 일관적 |
| 프롬프트 조정 | 가능 (유연) | 불가 (블랙박스) |

Week 04에서 LLM 재순위화를 사용하는 이유:
1. 추가 서비스/모델 배포 없이 기존 OpenAI API로 구현 가능
2. 프롬프트를 직접 설계하므로 동작 원리를 체감
3. 교육 목적에서 정확도 차이는 중요하지 않음

## 비용 분석

20개 후보 문서 기준:
- 입력: 프롬프트 ~200 토큰 + 문서 20개 × ~100 토큰 = ~2,200 토큰
- 출력: JSON 배열 ~50 토큰
- gpt-4o-mini: 입력 $0.15/1M + 출력 $0.60/1M
- **호출당 비용: ~$0.0004**

쿼리 1,000건/일이면 ~$0.40/일. Baseline 대비 정확도가 20%p 이상 올라간다면 충분히 정당화.

## 학습자가 자주 하는 질문

### "이거 결국 LLM한테 '답 찾아줘'라고 하는 거 아닌가?"

아니다. 핵심 차이:
- **RAG의 Generation**: "이 문서를 참고해서 답변을 생성해줘" → 자연어 답변
- **ReRanking**: "이 문서가 이 질문에 얼마나 관련 있는지 점수만 매겨줘" → 숫자 배열

ReRanker는 답변을 생성하지 않는다. 검색 결과의 **순서만** 바꾼다. 답변 생성은 그 다음 단계에서 별도로 한다.

### "Batch scoring vs Pairwise scoring?"

- **Batch**: 모든 문서를 한 프롬프트에 넣고 한 번에 점수 (Week 04 방식)
  - 장점: LLM 호출 1회, 비용 최소
  - 단점: 문서 순서가 점수에 영향 (position bias)
- **Pairwise**: 문서 2개씩 비교하여 "어느 쪽이 더 관련 있는지" 판단
  - 장점: 더 정확. position bias 없음
  - 단점: C(n,2) 비교 필요 → 20개 문서면 190번 호출

교육 목적에서는 Batch로 충분. Position bias가 걱정되면 문서 순서를 랜덤으로 셔플.

### "temperature는 어떻게 설정하나?"

0.0 또는 0.1. 점수 매기기는 **일관성**이 중요하지 창의성이 중요하지 않다. 같은 문서-쿼리 쌍에 매번 다른 점수가 나오면 평가가 무의미해진다.
