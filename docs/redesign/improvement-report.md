# Spring AI 부트캠프 커리큘럼 재설계 — 개선 보고

---

## 이 커리큘럼이 무엇인가

**Spring AI 부트캠프**는 Spring Boot 개발 경험은 있지만 AI 서비스 개발은 처음인 개발자를 위한 실습 커리큘럼입니다.

목표는 단순히 LLM API를 연결하는 것을 넘어, **"LLM 서비스를 만들고, 개선하고, 왜 그렇게 해야 하는지 설명할 수 있는"** 상태까지 도달하는 것입니다.

이를 위해 **"벽에 부딪히고 → 필요성을 체감하고 → 학습"** 하는 방식을 핵심 철학으로 삼았습니다. 먼저 단순한 방식으로 구현해서 한계를 직접 경험하게 하고, 그 다음에 고급 기법을 배우는 구조입니다.

---

## 무엇이 문제였나

한 바퀴를 완전히 돌린 후 한 가지 근본적인 문제를 발견했습니다.

### 핵심 문제: 벽이 생기지 않았다

커리큘럼의 핵심 철학은 **"먼저 한계에 부딪혀야 학습 동기가 생긴다"** 는 것입니다. 그런데 실제로 돌려보니 벽이 없었습니다.

**이유: 데이터가 너무 단순했습니다.**

기존 데이터는 FAQ 24개 항목, 17개 청크 수준이었습니다. 이 규모에서는 아무리 단순한 방식으로 검색해도 정확도가 96%가 나왔습니다. 그 결과 다음과 같은 역설이 발생했습니다.

> ReRanker, QueryTransform 같은 **고급 검색 전략을 적용했더니 오히려 성능이 떨어졌다.**
> (Top-1 정확도: Baseline 82% → ReRanker 적용 후 56%)

이는 기법의 문제가 아니라 **환경의 문제**였습니다. 고급 기법은 데이터가 복잡하고 검색이 어려울 때 비로소 효과를 발휘합니다. 너무 쉬운 데이터 위에서는 오히려 노이즈가 됩니다.

---

### 이외에 발견된 문제들

**① 미션에 수치가 하드코딩되어 있었다**

미션 문서에 "Baseline 정확도 40-50%", "검색 속도 4초" 같은 예상 수치가 적혀 있었지만, 실제로 측정해보면 전혀 달랐습니다(실측 1.3ms, Baseline 96%). 학습자가 미션을 수행하면서 "내 결과가 왜 미션 예시와 다르지?"라는 혼란을 겪게 됩니다.

**② 중간에 도메인이 끊겼다**

Week 01~07은 FAQ 챗봇을 점진적으로 발전시키는 연속된 경험이었습니다. 그런데 Week 08에서 갑자기 GitHub PR 리뷰 봇 도메인으로 전환됐다가, Week 10에서 다시 FAQ로 돌아왔습니다. 학습자 입장에서는 맥락이 끊기는 경험이었습니다.

**③ 힌트 시스템이 무력화되었다**

커리큘럼에는 3단계 힌트 카드 시스템이 있습니다. 스스로 생각해보고, 막히면 단계적으로 힌트를 여는 방식입니다. 그런데 스켈레톤 코드의 TODO 주석에 이미 정답(API 이름, 완성 코드 조각)이 적혀 있었습니다. 힌트를 열 필요가 없었습니다.

**④ 10주 완주가 현실적으로 어렵다**

순차적으로 10주를 전부 따라가야 하는 구조여서 중간에 멈추면 얻는 것이 없는 구조였습니다.

---

## 어떻게 개선했나

### 1. 커리큘럼 구조를 2-Stage로 재편

**기존**: Week 01 → 02 → ... → 10 (10주 고정 순차)

**변경**:

```
Stage 1 (필수, 약 2주)
  └── Naive RAG FAQ 챗봇을 처음부터 직접 만든다
  └── 복잡한 데이터로 인해 "벽"을 체감한다
  └── Stage 1만 완주해도 의미 있는 경험

Stage 2 (선택, 모듈별 독립)
  ├── M1: 벡터 DB (Qdrant)
  ├── M2: 검색 개선 (ReRanker, QueryTransform)
  ├── M3: 관측성 (메트릭, 트레이싱)
  ├── M4: Function Calling
  ├── M5: 로컬 모델 (Ollama)
  ├── M6: 멀티 에이전트
  ├── M7: 프로덕션 통합
  └── M8~M11: 심화 모듈
```

이 구조가 해결하는 것:

- **완주율 문제** → Stage 1(2주)만으로도 완결된 경험
- **도메인 단절** → 전체가 하나의 FAQ 챗봇 도메인으로 유지
- **수치 하드코딩** → Stage 1에서 직접 측정한 수치가 Stage 2의 학습 동기

---

### 2. 데이터를 완전히 교체

벽이 생기는 데이터를 설계하기 위해 **3-Layer 구조**로 재설계했습니다.

#### Layer 1 — 공식 FAQ (영어)

12개 카테고리, 약 52개 Q&A. 영어로 작성된 공식 문서입니다. 학습자가 한국어로 질문할 때 영어 문서와의 검색 미스가 자연스럽게 발생합니다.

#### Layer 2 — 정책 문서 (버전 충돌 의도 삽입)

- `current/` — 현재 정책 (반품 14일, 포인트 1%)
- `deprecated/` — 구버전 정책 (반품 7일, 포인트 3%/5%/7%)
- `internal/` — 내부 문서

두 버전의 문서가 벡터 DB에 함께 저장됩니다. 단순한 검색으로는 어떤 버전이 맞는지 판단하기 어렵습니다.

#### Layer 3 — 상담 로그 (노이즈 의도 삽입)

330건의 상담 대화 기록. `agent_jung`이라는 가상 상담사가 의도적으로 잘못된 정보를 제공하는 케이스가 포함됩니다 (반품 기간을 14일이 아닌 7일이라고 안내, 구버전 포인트 적립률 안내 등). 이 오답 로그가 벡터 DB에 섞이면서 검색 노이즈가 발생합니다.

#### 테스트 질문 100개 (난이도 3단계)

| 난이도 | 수량 | 유형 |
|--------|------|------|
| easy | 30개 | 단순 사실 확인 |
| medium | 44개 | 조건부 / 버전 충돌 / 비격식 한국어 |
| hard | 26개 | 멀티홉 추론 / 대화 맥락 기억 |

---

### 3. "벽"이 실제로 존재하는지 수치로 검증

데이터를 만든 후, Naive RAG로 실제로 평가해서 "벽"이 생기는지 확인했습니다. 5차례 반복 실험을 거쳐 최종 결과:

| 난이도 | Naive RAG 정확도 | 의미 |
|--------|-----------------|------|
| easy | 56.7% | 단순 질문은 절반 이상 해결됨 |
| medium | 54.3% | 조건부/버전 충돌 질문은 절반이 실패 |
| hard | **30.8%** | 어려운 질문은 대부분 실패 |

**벽이 존재한다는 증거:**

- easy vs hard 간 **약 26%p** 정확도 격차 — 명확한 난이도 차이
- 한국어 비격식체 질문(`"반품어케함? ㅠ"`) → 영어 FAQ 검색 실패율 62%
- 다문서 추론 / 대화 맥락 기억 질문 → 정확도 0%
- `agent_jung` 오답 로그가 top-5 검색 결과에 65% 비율로 포함되는 현상 확인

이 수치들이 Stage 2에서 배우는 기법들(ReRanker, QueryTransform, 멀티홉)의 **학습 동기**가 됩니다.

---

### 4. 힌트 시스템 복원

TODO 주석에서 정답 정보를 제거하고, 미션 문서에는 **"무엇을"만** 남겼습니다. **"어떻게"는** 별도 힌트 파일(`hints/HINT_01.md`, `HINT_02.md` 등)로 분리했습니다. 막히지 않으면 힌트를 열 필요가 없고, 막히면 단계적으로 접근할 수 있습니다.

---

### 5. 세부 버그 수정 및 품질 개선

| 문제 | 해결 |
|------|------|
| Spring AI 1.1.2 버그: 스트리밍 요청에 인식 불가 파라미터 포함 → HTTP 400 오류 | Jackson Mixin으로 직렬화 단계에서 제거 (스트리밍/비스트리밍 모두 커버) |
| Qdrant 버전이 고정되지 않아 클라이언트/서버 불일치 발생 | `v1.13.6`으로 버전 고정 |
| 테스트 실패 시 에러 원인이 출력되지 않음 | 전 모듈 테스트에 `andDo(print())` 추가 |
| 기본 모델이 구버전(`gpt-4o-mini`) | `gpt-4o-mini`로 교체 |
| M4 힌트에 더 이상 지원하지 않는 MCP 클라이언트(Claude Desktop) 안내 | OpenCode + Claude Code 설정으로 교체 |
| 미션 문서에 절대 수치 하드코딩 | "직접 측정 → 가설 → 개선" 사이클 구조로 교체 |

## 정리

| | 기존 | 개선 후 |
|--|------|---------|
| **구조** | 10주 고정 순차 | Stage 1(필수) + Stage 2(선택 모듈) |
| **데이터** | FAQ 24개, 단순 단일 언어 | 3-Layer 443개 청크, 버전 충돌/노이즈 포함 |
| **벽** | 없음 (Baseline 96%) | 존재 (hard 31%, 검색 실패 패턴 다수) |
| **힌트** | TODO 주석에 정답 포함 | 미션에 "무엇만", 힌트 파일에 "어떻게" |
| **수치** | 하드코딩된 예상값 | 직접 측정하는 구조 |
| **도메인** | Week 08에서 단절 | 전체 FAQ 챗봇 도메인 유지 |

**핵심 원칙은 그대로입니다.** 10주 동안 쌓아온 코드, 테스트, 문서, "벽에 부딪혀 배우는" 철학은 모두 유지됩니다. 바꾼 것은 그 철학이 **실제로 작동하도록** 만든 것입니다.
