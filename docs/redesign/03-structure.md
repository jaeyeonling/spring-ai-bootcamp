# Step 3: 새 커리큘럼 구조 설계

## 전체 구조

```
Stage 1: 환경 만들기 (2주)
  "이 데이터와 LLM API로 고객 질문에 답하는 서비스를 만들어라"
  → 벽을 체감한다

Stage 2: 개선 모듈 (11개, 선택적)
  Stage 1에서 느낀 불편함을 선택해서 해결한다
```

---

## Stage 1: 환경 만들기

### 미션

> 초록 코퍼레이션에 입사했습니다.
> 고객지원팀이 사용할 챗봇 REST API를 만들어주세요.
>
> 데이터는 여기 있습니다:
> - 공식 FAQ 문서
> - 내부 정책 문서
> - 고객 상담 로그
>
> LLM API를 사용하세요. 금요일까지요.

**그게 전부.** 추가 안내 없음. 알아서 해결.

### 제공물

- 데이터: 3-Layer 혼합 데이터 (1000+ 아이템)
- API 키: OpenAI (또는 공용 게이트웨이)
- 최소 스켈레톤: Spring Boot 프로젝트 + `POST /api/chat` 엔드포인트 껍데기
- 테스트 질문 100개 (자동 평가용)

### 미제공 (의도적)

- 임베딩, 벡터 검색, RAG에 대한 설명
- 데이터 로딩/파싱 코드
- 청킹 전략
- 평가 프레임워크

### 데이터가 만드는 벽

Stage 1의 벽은 **미션이 아니라 데이터가 만든다.** 학습자가 겪을 벽:

| 벽 | 원인 | Stage 2 연결 |
|----|------|-------------|
| 토큰 한계 | 3000+ 문서가 context window에 안 들어감 | → M1 벡터 DB |
| 포맷 혼재 | 마크다운 + JSONL + 버전 충돌 정책 문서 | → M1 ETL 파이프라인 |
| 검색 품질 | 3000건 상담 로그 노이즈 속에서 50개 FAQ를 못 찾음 | → M2 검색 품질 |
| 프롬프트 한계 | 시스템 프롬프트만으로 품질 개선에 한계 | Stage 1 내에서 직접 경험 |
| 품질 판단 불가 | 답변이 맞는지 틀리는지 자동으로 판단할 방법 없음 | → M3 관측성 & 평가 |
| 답변 모순 | FAQ vs 정책 문서 불일치 | → M6 멀티 에이전트 |
| 비용 증가 | 매 요청마다 대량 토큰 소비 | → M5 비용 최적화 |
| 대화 단절 | 이전 질문을 기억 못함 | → M8 대화 기억 |
| 응답 지연 | 전체 답변이 완성될 때까지 대기 | → M9 스트리밍 |
| 파싱 불안정 | LLM 응답 형식이 매번 달라짐 | → M10 구조화 출력 |
| 지식 정체 | 상담 로그에 좋은 답변이 있는데 FAQ에 반영이 안 됨 | → M11 데이터 피드백 루프 |

### 완료 기준

- `POST /api/chat`이 동작한다
- 3개 레이어 데이터를 어떤 방식으로든 활용한다
- 테스트 질문 100개에 대한 정확도를 측정할 수 있다
- **벽 리포트**: 겪은 문제와 한계를 문서로 정리한다

### 기간

2주 (자기 속도대로). 주차 구분 없는 하나의 미션.

### 선택 가이드

학습자가 Stage 1 벽 리포트를 보고 스스로 선택하되, 추천 경로를 안내:

```
최소 경로 (핵심만):        M1 → M2
실무 경로 (서비스 운영):    M1 → M2 → M3 → M4 → M8
전체 경로 (풀 사이클):     M1 → M2 → M3 → M4 → M5~M11 → M7
```

### 모듈 상세

#### M1: 벡터 DB & ETL (기존 week03)
- **벽**: "1000개 문서를 프롬프트에 넣을 수 없다"
- **배우는 것**:
  - 임베딩이란 무엇이고 왜 필요한가
  - 벡터 검색 (코사인 유사도, HNSW 인덱스)
  - Qdrant 설정 및 운영
  - ETL 파이프라인 설계 (Read → Transform → Write)
  - 멀티 포맷 파싱 (마크다운, YAML frontmatter, JSONL)
  - 메타데이터 설계 (레이어, 카테고리, 버전, 날짜)
- **완료 기준**: Qdrant에 1000+ 문서 적재, 메타데이터로 레이어별 필터링 가능
- **기존 코드**: `IngestionService`, `TikaDocumentReader`, Qdrant 설정

#### M2: 검색 품질 (기존 week04)
- **벽**: "검색 결과 상위에 엉뚱한 문서가 올라온다"
- **배우는 것**:
  - ReRanker — 왜 필요한가, 1000+ 청크 환경에서 노이즈 필터링 효과
  - 쿼리 변환 — 원본 질문을 검색에 최적화된 형태로 재작성
  - 메타데이터 필터링 — 레이어별, 버전별, 날짜별 사전 필터
  - 하이브리드 검색 — 벡터 + BM25 키워드 결합 (고유명사, 주문번호 등)
  - 청크 사이즈 튜닝 — 크기가 검색 품질에 미치는 영향
  - **평가 기반 개선 사이클** — 측정 → 가설 → 적용 → 재측정
- **핵심 변화**: 1000+ 소형 청크 + 노이즈 환경에서 ReRanker가 **실제로 효과 발휘**
- **완료 기준**: Baseline 대비 Top-1 정확도 +15%p 이상, 개선 과정을 수치로 문서화
- **기존 코드**: `RetrievalStrategy`, `ReRankingRetrieval`, `QueryTransformRetrieval`

#### M3: 관측성 & 평가 (기존 week05 + 평가 확장)
- **벽**: "왜 틀렸는지 모르겠다", "답변이 맞는지 틀리는지 자동으로 판단할 방법이 없다"
- **배우는 것**:
  - **관측성**
    - RAG 파이프라인 단계별 실패 지점 추적 (검색 실패 vs 생성 실패)
    - Micrometer 메트릭 — 요청별 비용 추적, 지연시간 분포
    - OpenTelemetry 분산 트레이싱 — 검색 → LLM → 응답 전체 경로
    - 품질 모니터링 — 프로덕션에서 정확도 저하 감지 (모델 변경, 데이터 변경 시)
  - **평가 파이프라인**
    - 평가 기준 설계 — 관련성, 사실 일치, 완전성을 어떻게 측정할 것인가
    - RelevancyEvaluator + FactCheckingEvaluator 활용
    - 환각 탐지 — 검색 문서에 근거하지 않는 답변 감지
    - 프롬프트 검증 — 출력이 지시사항(역할, 톤, 범위)을 따르는지 확인
    - 전략 간 A/B 비교를 수치로 판단 — "이 프롬프트가 나은가, 저 프롬프트가 나은가?"
  - **가드레일**
    - 답변 범위 제한 — FAQ에 없는 내용에 대해 "모르겠습니다" 응답 강제
    - 프롬프트 인젝션 기본 방어
- **완료 기준**: 실패 질문의 원인을 자동 분류 + 평가 파이프라인으로 전략 비교 가능
- **기존 코드**: `ObservabilityConfig`, `MetricsService`, `FactCheckingEvaluator`, `EvaluationRunner`

#### M4: Tool Use & MCP (기존 week07 + week09 통합)
- **벽**: "문서에 없는 실시간 정보를 답할 수 없다", "이 기능을 다른 도구에서도 쓰고 싶다"
- **배우는 것**:
  - @Tool, Function Calling 기초 — LLM이 함수를 선택하고 호출
  - **Tool description 설계** — 설명 문구가 곧 라우팅 로직, 좋은 설명 vs 나쁜 설명의 차이
  - Tool vs RAG 판단 기준 — 언제 검색이고 언제 함수 호출인가
  - Tool 실패 시 에러 핸들링 / 폴백 전략
  - Tool 체이닝 — 하나의 Tool 결과를 다른 Tool 입력으로
  - Reflection 패턴 — 생성 → 검증 → 재시도
  - MCP 프로토콜 — Tool을 표준 인터페이스로 외부에 노출
  - MCP Resources & Prompts — Tool 이외의 MCP 프리미티브
- **완료 기준**: LLM이 Tool을 자동 선택하여 호출 + MCP 클라이언트에서 동일 Tool 호출 가능
- **기존 코드**: `OrderTools`, `FaqSearchTool`, `ReflectionService`, `FaqMcpService`, MCP Boot Starter

#### M5: 비용 최적화 (기존 week06)
- **벽**: "API 비용이 너무 많이 나온다"
- **배우는 것**:
  - 비용 구조 분석 — 토큰 단가 × 사용량, 어디서 비용이 발생하는가
  - Ollama 로컬 모델 — 설치, 설정, Spring AI 통합
  - 모델 라우팅 전략 — 질문 난이도별 분배 (쉬운 건 작은 모델, 어려운 건 큰 모델)
  - 시맨틱 캐싱 — 유사 질문 재사용으로 LLM 호출 절감
  - 프롬프트/컨텍스트 최적화 — 불필요한 토큰 줄이기
  - 비용 모니터링 + 예산 관리 — 월간 예산 초과 알림
- **완료 기준**: 동일 품질 대비 비용 50%+ 절감, 비용 추적 대시보드
- **기존 코드**: `ModelRoutingService`, Ollama 설정, K8s 매니페스트

#### M6: 멀티 에이전트 (기존 week08, 도메인 변경)
- **벽**: "FAQ와 정책이 다른 답을 주는데 어떤 게 맞는지 모르겠다"
- **배우는 것**:
  - 멀티 에이전트가 **진짜 필요한 순간** vs 단일 에이전트 + Tool로 충분한 순간
  - Chain 패턴 — 순차 처리, 컨텍스트 누적
  - Orchestrator-Worker 패턴 — 병렬 처리, 결과 합성
  - Routing 패턴 — 질문 유형별 전문 에이전트 분배
  - 에이전트 간 충돌/모순 해결 — FAQ vs 정책이 다른 답을 줄 때 어떻게?
  - 에이전트 실패 시 폴백 전략
- **선행**: M4 (에이전트가 Tool 사용)
- **핵심 변화**: PR 리뷰 → FAQ 도메인 (FaqAgent, PolicyAgent, ChatHistoryAgent)
- **완료 기준**: 교차 소스 질문 정확도 +20%p 이상 개선
- **기존 코드**: `Agent` 인터페이스, `OrchestratorService` (도메인만 교체)

#### M7: 프로덕션 통합 (기존 week10)
- **벽**: "이걸 실제로 서비스에 배포하려면?"
- **배우는 것**: Docker Compose 통합, 운영 체크리스트, Stage 1 vs 최종 비교
- **완료 기준**: 전체 스택 Docker Compose 실행, 테스트 질문 80%+ 정확도
- **기존 코드**: week10 전체 (도메인 에이전트 업데이트)

#### M8: 대화 기억 (신규)
- **벽**: "이전에 물어본 걸 또 물어봐야 한다"
- **배우는 것**:
  - ChatMemory 기초 — Spring AI의 대화 컨텍스트 관리
  - 메모리 윈도우 전략 — 슬라이딩 윈도우, 요약 기반, 선택적 기억
  - 토큰 예산 관리 — 대화가 길어지면 컨텍스트가 차오르는 문제
  - **대화형 RAG** — 이전 대화 맥락을 검색 쿼리에 반영
  - 세션 관리 — 사용자별 대화 분리, 세션 만료
- **완료 기준**: 멀티턴 대화에서 이전 맥락을 활용한 답변 + 토큰 예산 내 유지
- **기존 코드**: 없음 (Spring AI ChatMemory API 활용)

#### M9: 스트리밍 & 응답 제어 (신규)
- **벽**: "답변이 완성될 때까지 빈 화면을 보고 있어야 한다", "잘못된 방향으로 가는데 멈출 수가 없다"
- **배우는 것**:
  - Spring AI stream() API, SSE (Server-Sent Events) — 기본 스트리밍
  - 클라이언트 인터럽트 — 사용자가 도중에 취소하면 LLM 호출 중단
  - 토큰 절약 — 인터럽트 시 불필요한 생성 비용 차단
  - 스트리밍 환경에서의 에러 핸들링 — 중간에 실패하면?
  - 스트리밍 + Tool Use 조합 — Tool 호출 결과를 기다리는 동안 UX 처리
  - 스트리밍 환경에서의 관측성 — OTel 트레이싱이 스트리밍에서도 동작하는가
- **선행**: 없음 (Stage 1 직후 바로 적용 가능, 다만 Tool Use/관측성 조합은 M4/M3 이후 심화)
- **완료 기준**: SSE 스트리밍 응답 + 클라이언트 인터럽트 시 LLM 호출 중단 + 중단 시 토큰 절약 확인
- **기존 코드**: 없음 (Spring AI Flux<ChatResponse> 활용)

#### M11: 데이터 피드백 루프 (신규)
- **벽**: "상담 로그 3000건에 좋은 답변이 있는데 FAQ에 반영이 안 된다", "같은 질문이 반복되는데 지식이 쌓이지 않는다"
- **배우는 것**:
  - 상담 로그에서 패턴 추출 — 반복 질문 감지, 빈도 분석
  - 자동 FAQ 후보 생성 — 상담사의 좋은 답변을 FAQ 형식으로 변환
  - 품질 검증 파이프라인 — 생성된 FAQ 후보가 기존 정책과 일관되는지 자동 검증
  - 지식 베이스 갱신 — 검증된 FAQ를 벡터 DB에 자동 반영
  - 데이터 드리프트 감지 — 새로운 유형의 질문 증가 알림
  - 피드백 루프 설계 — 상담 → 추출 → 검증 → 반영 → 품질 측정 사이클
- **선행**: M1 (벡터 DB) + M3 (평가 파이프라인으로 품질 검증)
- **완료 기준**: 상담 로그에서 FAQ 후보 자동 추출 + 검증 후 벡터 DB 반영 + 정확도 개선 확인
- **기존 코드**: 없음 (Spring AI + 배치 처리 설계)

#### M10: 구조화 출력 (신규)
- **벽**: "LLM 응답 형식이 매번 달라서 파싱이 깨진다"
- **배우는 것**:
  - Spring AI Structured Output — BeanOutputConverter, JSON 스키마 강제
  - 출력 스키마 설계 — 어디까지 강제할 것인가, 유연성과 안정성의 트레이드오프
  - 스키마 위반 시 재시도 전략 — 실패 감지 + 자동 재요청
  - 스트리밍 + 구조화 출력 조합 — 부분 파싱, 점진적 스키마 검증
  - 구조화 출력 vs 자유 텍스트 — 언제 강제하고 언제 풀어줄 것인가
- **선행**: 없음 (Stage 1 직후 바로 적용 가능)
- **완료 기준**: LLM 응답이 항상 정해진 JSON 스키마를 따름 + 위반 시 자동 재시도
- **기존 코드**: 없음 (Spring AI BeanOutputConverter 활용)
