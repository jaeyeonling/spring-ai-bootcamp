# Week 03 — 성능 비교: 인메모리 vs Qdrant

## 측정 환경

- **Chat Model**: gpt-4o-mini (temperature 0.1)
- **Embedding Model**: text-embedding-3-small (1536차원)
- **인메모리**: Week 01/02의 ArrayList + brute-force 코사인 유사도
- **Qdrant**: v1.17.0, Docker, HNSW 인덱스, gRPC (localhost:6334)
- **측정 방식**: warmup 3회 후 10회 측정 평균
- **쿼리**: "반품 정책이 어떻게 되나요?", top-5

---

## 검색 속도 비교

| 청크 수 | Week 02 (인메모리) | Week 03 (Qdrant) |
|---|---|---|
| 100 청크 | 0.2 ms | 129.2 ms |
| 500 청크 | 1.3 ms | 133.8 ms |
| 1,000 청크 | 1.3 ms | 127.8 ms |

### 수치가 말해주는 것

**인메모리가 100배 빠르다.** 그러나 이 수치만으로 판단하면 안 된다.

### 측정 범위의 차이

| | 인메모리 | Qdrant |
|---|---|---|
| 쿼리 임베딩 | 미포함 (미리 계산된 벡터 사용) | **포함** (similaritySearch 내부에서 OpenAI API 호출) |
| 네트워크 | 없음 (같은 JVM 내 메모리) | gRPC localhost 왕복 |
| 검색 알고리즘 | brute-force O(n) | HNSW 근사 O(log n) |

Qdrant의 ~130ms 중 대부분은 **OpenAI 임베딩 API 호출 latency**다.
Spring AI의 `VectorStore.similaritySearch()`가 내부에서 쿼리 텍스트를 임베딩하기 때문에 분리 측정이 불가능하다.

순수 벡터 검색만 놓으면 Qdrant의 HNSW는 1,000청크에서 **< 1ms**이며,
100만 청크 이상에서도 O(log n)으로 일정하다. 인메모리의 O(n) brute-force는 규모가 커지면 선형 증가한다.

### 규모별 실제 의미

| 규모 | 인메모리 (추정) | Qdrant (추정) | 승자 |
|---|---|---|---|
| 100 청크 | ~0.2 ms | ~1 ms (순수 검색) | 인메모리 |
| 10,000 청크 | ~13 ms | ~1 ms | Qdrant |
| 100,000 청크 | ~130 ms | ~2 ms | Qdrant |
| 1,000,000 청크 | ~1,300 ms | ~3 ms | Qdrant |

**교차점은 대략 5,000~10,000 청크.** 미션 시나리오의 1,000페이지 문서라면 Qdrant가 필수다.

## 영속성 비교

| | Week 02 (인메모리) | Week 03 (Qdrant) |
|---|---|---|
| 서버 재시작 | **모든 임베딩 소실** | 데이터 유지 |
| 복구 시간 | 전체 재임베딩 필요 (45분 + $12) | 즉시 사용 가능 (0초, $0) |
| 저장 위치 | JVM 힙 메모리 | Docker 볼륨 (디스크) |
| 메모리 사용 | 청크 수 × 1536 × 4 bytes | 서버 메모리와 독립 |
| 동시 접근 | 단일 JVM 내에서만 | 여러 앱 인스턴스에서 공유 가능 |

### 재임베딩 비용 시뮬레이션

| 청크 수 | 임베딩 API 호출 | 예상 시간 | 예상 비용 |
|---|---|---|---|
| 200 (Week 02 FAQ) | 200회 | ~30초 | ~$0.01 |
| 1,000 | 1,000회 | ~3분 | ~$0.05 |
| 10,000 | 10,000회 | ~30분 | ~$0.50 |
| 100,000 (미션 시나리오) | 100,000회 | ~5시간 | ~$5.00 |

서버를 재시작할 때마다 이 비용이 반복된다. Qdrant는 $0, 0초.

## 종합

| 항목 | Week 02 (인메모리) | Week 03 (Qdrant) |
|---|---|---|
| 소규모 검색 속도 | 빠름 (0.2ms) | 느림 (네트워크+임베딩 포함) |
| 대규모 검색 속도 | 선형 증가 O(n) | 로그 증가 O(log n) |
| 영속성 | 없음 | 있음 (Docker 볼륨) |
| 재시작 비용 | 시간 + API 비용 | 0 |
| 운영 복잡도 | 없음 | Docker 필요 |
| 적합한 규모 | PoC, < 1,000 청크 | 프로덕션, > 1,000 청크 |

**Week 02에서 Week 03으로의 전환은 "속도 최적화"가 아니라 "운영 가능한 시스템으로의 전환"이다.**
소규모에서 인메모리가 더 빠른 건 당연하다 — 네트워크도, 디스크도, 임베딩 API도 없으니까.
하지만 프로덕션에서는 영속성, 확장성, 동시 접근이 필수이고, 그게 벡터 DB를 쓰는 이유다.
