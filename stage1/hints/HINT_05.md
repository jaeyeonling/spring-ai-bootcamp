# 힌트 05: 돌아가긴 한다 — 이제 뭘 개선해야 하는가

`POST /api/chat`이 동작합니다. 테스트도 통과합니다.

지금 만든 것의 상태를 솔직하게 평가해보세요.

## 자가 진단 체크리스트

아래 항목을 직접 확인해보세요:

```
[ ] 정확도 측정: 테스트 질문 100개 중 몇 %가 정확한가?
[ ] 비용 측정: 100개 요청에 얼마가 드는가? 1,000개라면?
[ ] 속도 측정: 평균 응답 시간은? p95는?
[ ] 실패 패턴: 어떤 유형의 질문에서 주로 틀리는가?
[ ] 데이터 활용: Layer 1/2/3를 모두 쓰고 있는가?
```

## 일반적인 Stage 1 결과

솔직히 말하면, 대부분의 구현이 이 범위에 있습니다:

| 지표 | 일반적인 결과 |
|------|-------------|
| 전체 정확도 | 25-40% |
| Easy 질문 | 60-70% |
| Medium 질문 (교차 소스) | 15-25% |
| Hard 질문 (구어체, 상담 로그) | 5-15% |
| 요청당 비용 (토큰 과다) | 예상보다 높음 |

이 수치는 **실패가 아닙니다.** 이것이 출발점입니다.

## 벽 리포트 작성하기

`wall-report.md`를 작성하세요. 형식은 자유롭지만, 이 질문에 답하세요:

1. **가장 많이 실패한 질문 유형은?** (예: 교차 소스가 필요한 질문)
2. **왜 실패했다고 생각하는가?** (예: 상담 로그 노이즈, 구버전 정책)
3. **지금 방식의 가장 큰 한계는?** (예: 토큰 비용, 검색 품질)
4. **개선한다면 어디서부터 시작하겠는가?**

이 리포트가 Stage 2 모듈 선택의 기준입니다.

## Stage 2 진입

벽 리포트를 바탕으로 어떤 모듈을 선택할지 결정하세요.

```
정확도가 낮다    → M1 (벡터 DB) → M2 (검색 품질)
비용이 높다      → M5 (비용 최적화)
실패 원인 모름   → M3 (관측성 & 평가)
응답이 느리다    → M9 (스트리밍)
답변 일관성 없음 → M10 (구조화 출력)
대화가 단절됨    → M8 (대화 기억)
```

대부분은 **M1 → M2** 순서가 가장 효과적입니다.
M1이 벡터 DB를 구축하면, M2의 고급 검색 전략이 실제로 효과를 발휘합니다.
