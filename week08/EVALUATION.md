# Week 08 — 멀티 에이전트 평가: 단일 프롬프트 vs 멀티 에이전트 워크플로우

## 배경

FAQ 챗봇 팀이 5명으로 성장하면서 PR 리뷰 부담이 커졌다.
"코드 리뷰 + 테스트 제안 + 문서 업데이트"를 하나의 프롬프트로 처리하면 결과가 얕다.
멀티 에이전트 워크플로우가 이 문제를 해결하는지 평가한다.

---

## 평가 대상 PR Diff

```java
public User findById(String id) {
    return userRepository.findById(id).orElse(null);  // null 반환
}

public void deleteUser(String id) {
    userRepository.deleteById(id);  // 존재 확인 없음
}

public User updateEmail(String id, String email) {
    User user = userRepository.findById(id).get();  // NoSuchElementException 가능
    user.setEmail(email);                             // 이메일 검증 없음
    return userRepository.save(user);
}
```

이 diff에는 의도적으로 심어진 이슈가 있다:
- `orElse(null)` → 호출자에 NPE 전파
- `.get()` → `NoSuchElementException` 가능
- 이메일 검증 없음 → 잘못된 형식 저장 가능
- `deleteUser`에서 존재 확인 없음

## 단일 프롬프트 방식

### 프롬프트

```
당신은 시니어 엔지니어입니다. PR 변경 사항(diff)을 바탕으로 다음을 수행하세요:
1. 버그, 스타일 문제, 보안 문제를 코드 리뷰합니다.
2. 단위 및 통합 테스트 케이스를 제안합니다.
3. 문서 업데이트를 제안합니다.
결과를 구조화된 형식으로 반환하세요.
```

### 예상 결과 특성

- LLM이 3가지 작업을 동시에 다루려니 각각이 얕아짐
- 코드 리뷰: 주요 이슈 1~2개 언급하지만 엣지 케이스 놓침
- 테스트: "findById 테스트를 작성하세요" 수준의 일반적 제안
- 문서: "API 문서를 업데이트하세요" 수준의 모호한 제안

| 측면 | 수치 |
|------|------|
| LLM 호출 횟수 | 1회 |
| 예상 지연시간 | 5~10초 |
| 예상 토큰 비용 | ~$0.0003 |

## 멀티 에이전트 방식

### Chain 패턴

```
CodeReview(diff, "") → review
TestWriter(diff, review) → tests  (리뷰 이슈를 타겟으로)
DocWriter(diff, review + tests) → docs  (전체 맥락 반영)
```

| 측면 | 수치 |
|------|------|
| LLM 호출 횟수 | 3회 (순차) |
| 실측 지연시간 | ~30~45초 (순차 합산) |
| 예상 토큰 비용 | ~$0.0009 |

**장점**: TestWriter가 CodeReview의 "orElse(null)" 이슈를 보고 해당 케이스의 테스트를 우선 작성.

### Orchestrator-Worker 패턴

```
분해(diff) → plan
CodeReview(diff, plan) ┐
TestWriter(diff, plan) ├── 병렬
DocWriter(diff, plan)  ┘
합성(review + tests + docs) → final report
```

| 측면 | 수치 |
|------|------|
| LLM 호출 횟수 | 5회 (분해 + 3 병렬 + 합성) |
| 실측 지연시간 | ~39초 (분해 10s + 병렬 19s + 합성 10s) |
| 예상 토큰 비용 | ~$0.0015 |

**장점**: 병렬 실행으로 Chain보다 빠를 수 있음. 합성 단계에서 중복 제거.

## 비교 분석

| 차원 | 단일 프롬프트 | Chain | Orchestrator-Worker |
|------|------------|-------|---------------------|
| **코드 리뷰 깊이** | 얕음 (주요 이슈 1~2개) | 깊음 (전문 프롬프트) | 깊음 (전문 프롬프트) |
| **테스트 구체성** | 일반적 ("테스트 작성") | 높음 (리뷰 이슈 타겟) | 보통 (리뷰 참조 불가) |
| **문서 관련성** | 모호함 | 높음 (전체 맥락) | 보통 (plan만 참조) |
| **총 지연시간** | ~5~10초 | ~30~45초 | ~39초 |
| **LLM 호출** | 1회 | 3회 | 5회 |
| **토큰 비용** | $0.0003 | $0.0009 (3x) | $0.0015 (5x) |
| **에이전트 간 맥락** | N/A | 순차 전파 | 없음 (독립) |
| **에러 전파 위험** | 없음 | 높음 | 낮음 |

## 워크플로우 패턴별 적합 시나리오

### Chain이 적합한 경우

- **결과 간 의존성이 있을 때**: TestWriter가 CodeReview 결과를 참조해야 할 때
- **품질이 속도보다 중요할 때**: 프로덕션 배포 전 최종 리뷰
- **에이전트 수가 적을 때**: 3~4개 에이전트에서 순차 실행 오버헤드가 수용 가능

### Orchestrator-Worker가 적합한 경우

- **에이전트가 독립적일 때**: 각 에이전트가 서로의 출력이 필요 없을 때
- **속도가 중요할 때**: CI/CD 파이프라인에서 빠른 피드백 필요
- **에이전트 수가 많을 때**: 5개 이상 에이전트에서 순차 실행이 너무 느릴 때
- **부분 실패를 허용할 때**: 한 에이전트 실패가 전체를 멈추지 않아야 할 때

### Routing이 적합한 경우 (미구현, 분석만)

- **입력 유형에 따라 처리가 다를 때**: 순수 문서 변경 PR → DocWriter만 실행
- **비용 최적화**: 불필요한 에이전트 실행 방지
- Week 07의 Function Calling에서 LLM이 "어떤 툴을 쓸지" 결정하는 것과 동일한 원리

## 비용 효율성 분석

월 100건 PR 기준:

| 방식 | 건당 비용 | 월 비용 | 품질 |
|------|---------|--------|------|
| 단일 프롬프트 | $0.0003 | $0.03 | 낮음 |
| Chain | $0.0009 | $0.09 | 높음 |
| Orchestrator | $0.0015 | $0.15 | 높음 |
| 시니어 엔지니어 30분 | ~$25 | $2,500 | 최고 |

**결론**: 멀티 에이전트가 단일 프롬프트보다 3~5배 비싸지만, 시니어 엔지니어 시간 대비 압도적으로 저렴하다. "첫 번째 패스 자동화"로 사용하면 ROI가 매우 높다.

### 권장 전략

```
PR 크기에 따른 라우팅:
  문서 전용 변경  → DocWriter만 (1회 호출)
  소규모 변경     → Chain (3회 호출, 맥락 있는 깊은 리뷰)
  대규모 변경     → Orchestrator-Worker (5회 호출, 빠른 병렬 처리)
```

이 라우팅은 Week 07의 Routing 개념과 동일하다 — LLM(또는 규칙)이 입력 특성을 판단해 적절한 워크플로우로 분기한다.
